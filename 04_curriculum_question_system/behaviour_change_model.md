# Behaviour Change Model

Current status: canonical planning model for BecomingOS curriculum and growth-loop design. This document is educational and non-clinical. It does not approve public MVP build, production readiness, implementation work, therapy, diagnosis, treatment, crisis intervention, or professional advice.

Primary research source: `03_research_validation/evidence_based_growth_systems_report.md`.

## Model

BecomingOS uses this behaviour-change planning loop:

```text
diagnosis flow -> Today Directive -> if-then plan -> completion tracking -> failure diagnosis -> adaptive reset
```

This loop is a product-planning interpretation of evidence around COM-B, implementation intentions, self-monitoring, feedback, cues, habit formation, and non-shaming adaptation.

## Components

| Component | Role | Evidence basis | Boundary |
|---|---|---|---|
| Diagnosis flow | Identify whether the barrier is capability, opportunity, motivation, overload, weak cue, low confidence, or context mismatch. | COM-B and problem-solving evidence. | Behavioural lens only; not clinical diagnosis. |
| Today Directive | Present one feasible next action, plus a backup and reduced version where appropriate. | Implementation inference from action planning, cueing, and self-monitoring evidence. | Draft planning support; user can edit or reject. |
| If-then plan | Convert the intention into "If [cue/context], then I will [action]." | Implementation intentions evidence. | Educational action-planning tool, not treatment. |
| Completion tracking | Record whether the action happened and whether a reduced version was used. | Self-monitoring evidence. | Avoid punitive streak pressure and sensitive free-text by default. |
| Failure diagnosis | Ask what got in the way and reclassify the barrier. | COM-B, feedback, and adaptive planning evidence. | Non-shaming; not pathology, diagnosis, or blame. |
| Adaptive reset | Adjust timing, difficulty, cue, support, or minimum viable action. | Feedback, competence support, habit formation, and Bad Day Mode inference. | Keeps user agency; no guaranteed outcomes. |

## COM-B Use

COM-B is used as a diagnostic lens for behaviour, not as a clinical diagnosis. It helps distinguish:

- Capability: knowledge, skill, energy, or confidence gap.
- Opportunity: time, environment, resources, social context, or friction gap.
- Motivation: value alignment, desire, avoidance, competing priorities, or readiness gap.

BecomingOS should not label users or infer medical, mental health, addiction, or clinical conditions from COM-B answers.

## Action Planning

Implementation intentions should be the default structure for action planning:

```text
If it is [time/cue/context] and [condition], then I will [specific action].
```

Plans should include a small enough action to be feasible, a cue, and where useful, a fallback or Bad Day version.

## Review And Feedback

Self-monitoring and feedback should help users learn from outcomes:

- What happened?
- What cue or context was present?
- What made it easier or harder?
- What should change next time?

Feedback should be calm, practical, and non-shaming. Missed actions should trigger plan improvement, not guilt.

## Bad Day Mode

Bad Day Mode scales down the plan without shame. It may suggest a reduced version, shorter duration, easier context, delayed timing, or reset plan.

Bad Day Mode must not imply therapy, crisis care, diagnosis, or treatment. If crisis or immediate danger appears, BecomingOS should stop growth coaching and signpost appropriate support.
